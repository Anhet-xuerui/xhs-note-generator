# 小红书多角色笔记生成

七个角色在一个受控的讨论循环里互相挑刺，产出一篇能直接发的小红书图文笔记（标题 / 封面文案 / 正文 / 标签）；
同时把「多角色到底比单次生成好在哪、值不值这个成本」做成可复现的实验。

**为什么值得看**：这个项目的重点不是「用 LangGraph 串了七个 prompt」，而是两样更稀缺的东西——
一组**结构化的判定信号**（判定卡 + 判别力与一致性验证），和一组**敢给负面结论的消融实验**。

| 当前状态 | |
|---|---|
| 测试 | 161 passed（离线，约 3 秒） |
| 质量门 | `ruff` 0 / `mypy` 0（39 模块） |
| 冻结契约 | `xhs-invariants` 6/6（信息隔离 / schema 冻结 / 轮次上限 / 单一评分口径 / 不采集平台数据） |
| 一次真实运行 | 8 次调用、**0.037 元**、35 秒 |

## 三条关键设计

**1. 信息隔离：七个角色不能看到同一段 context**

| 隔离 | 做法 | 不这么做会怎样 |
|---|---|---|
| 读者看不到 `real_material` | `context.py` 白名单裁剪 | 它会替作者打同情分，「像不像真人」变成「作者是不是真经历过」 |
| 策划看不到成稿 | 只给约束卡 + 上一轮判定卡 | 看到稿子它就开始替稿子辩护——模型最稳定的行为之一 |
| 主笔看不到规则库全文 | 只给守门人的具体命中项（当前流程里守门人在主笔之后跑，所以主笔实际拿到的是空列表；命中项只回喂给人味校订） | 把整本规则塞给主笔，它会为了绕规则把句子写得又长又空 |

这不是文档里的君子协定：`build_reader_context` / `build_planner_context` / `build_writer_context` 是唯一入口，
有单测断言三条隔离，`xhs-invariants` 的 C3 是同一套断言之外的 AST 二次检查（本地脚本，可接 CI）。

**2. 读者换一家厂商**

写作用 DeepSeek，读者用 GLM。代码里是真的两个 provider，不是两个 temperature：
`READER_*` 缺失时启动即报错，与主笔「同 base_url 同模型」也会被拒绝（否则 E2 直接作废）。
客户端的连接缓存按 `(base_url, api_key)` 维度，避免两家共用一个 base_url 时串了 key。

**3. 规则先筛，模型后改**

AI 味检测和违禁词都是**程序化规则**，模型只做两件事：按命中项改写、判断命中是不是误报。
「最 / 第一」这类词误报极多（最后、第一次），这正是守门人值得存在的那一半工作——
纯正则做不了，纯模型不可靠。

## 评测结果

> 五次重复的完整报告：[报告](docs/samples/eval-report-5repeats.md) / [HTML](docs/samples/eval-report-5repeats.html)；原始逐轮指标在 `docs/samples/pairwise-repeat-*.json`。
> 判据与实验设计见 [设计文档 §12](docs/superpowers/specs/2026-10-23-xhs-multiagent-design.md)。

### 五次重复（请求 10 个主题，实际 7–8 个产出成稿；每次重新生成语料）

单次跑的数字会骗人——同一套代码，B 组通过率我见过 12%、26%、38%。所以做 5 次重复，报均值与 bootstrap 95% 区间。

| 指标 | 均值 [95% CI] | 能不能当结论 |
|---|---|---|
| E1 绝对打分正确率 | 42% [34%, 51%] | ✅ 明确低于 80% 判据 |
| E1 Kendall τ | 0.61 [0.59, 0.64] | ✅ |
| E1 **两两比较**正确率 | **96%** [95%, 98%] | ✅ 与绝对打分区间不重叠 |
| E1 两两比较位置不一致率 | 20% [16%, 24%] | — |
| E2 click κ | 0.68 [0.52, 0.84] | ⚠️ 均值过线，区间跨线 |
| E2 save κ | 0.69 [0.58, 0.79] | ⚠️ 下界擦线 |
| E2 score ρ | 0.80 [0.75, 0.85] | ✅ |
| **E3 A vs B** | A 胜 26% [13%, 36%] → **B 胜 74%** | ✅ 上界 36% < 50% |
| E3 B vs C | B 胜 63% [43%, 80%] | ⚠️ 区间跨 50% |
| E3 A vs C | A 胜 61% [46%, 81%] | ⚠️ 区间跨 50% |
| E3 B · tokens / 成本 | 47.7k [38.4k, 54.5k] / 0.20 元 [0.16, 0.23] | ✅ |

**三条站得住的结论：**

1. **判定卡该用两两比较。** 同一批稿：绝对打分 42%［34, 51］，两两比较 96%［95, 98］——区间完全不重叠。测量方式比指标本身更决定判别力，这是全项目最硬的一条。
2. **讨论循环打赢裸模型，代价是 8 倍钱。** A 组胜率 26%，上界 36% 都没到 50%。同一批的绝对量：B 46,559 tokens / 0.197 元，A 3,720 tokens / 0.024 元——**token 12.5 倍、成本 8.1 倍**。（注意 B 只跑讨论循环，不含封面/人味校订/守门人，所以这是「讨论循环」的账，不是「七角色产品」的账。）
3. **一致性大体达标但不稳。** click κ 0.68、save κ 0.69 均值都过了 0.6，但区间下界 0.52 / 0.58 说明「换一个样本批次可能掉到线下」。要写成「可复现」，样本还得再加一个量级。

**还不能说的两句（照实写）：**

- **同厂商读者（C）是不是更差，5 轮还没定。** B 胜 C 63%、A 胜 C 61%，两个区间都跨过 50%。三轮时看到的「C 最差」有方向，但幅度没被区间确认——所以只能写「方向一致，未达显著」。
- **通过率系列全部作废。** 之前几版 README 里的「通过率 0% → 38%」之类数字，是用只有 42% 排序能力的绝对判定卡量的，已从结论里移除。

评测口径：三组成稿都由**同一个读者实例**事后打分；A 组没有 `Verdict`，它的评分调用成本单列。
每次跑评测记录读者 prompt 的 sha256 指纹与模型名——否则「你改过 prompt 之后还叫同一组数据吗」答不上来。

## 怎么跑

```bash
cd backend
cp .env.example .env          # 填两组 key：写作侧 + 读者侧（必须不同厂商）
uv sync

# 构建前端（Vue 3 + Vite），产物由后端直接托管
cd ../frontend && pnpm install && pnpm build && cd ../backend

# 起本地服务：浏览器打开 http://localhost:8000
uv run uvicorn app.api.app:create_app --factory --port 8000

# 或者前后端分离开发（Vite 5173 代理到 8000，热更新）
cd ../frontend && pnpm dev

# 跑一次生成（约 35 秒、约 0.04 元）
uv run python -m app.cli run --persona scripts/personas/p01.json \
  --topic "租房第一年我终于搞清楚的事" --trace-out data/traces/r1.jsonl

# 换 LangGraph 引擎跑（落 checkpoint 到 data/checkpoints.sqlite，可回放）
uv run python -m app.cli run --persona scripts/personas/p01.json \
  --topic "租房第一年" --engine graph

# 渲染单文件过程报告
uv run python -m app.cli report --trace data/traces/r1.jsonl --out data/report.html

# 评测（--dry-run 不花钱）
uv run python -m app.cli eval --dry-run --out ../eval/out
uv run python -m app.cli eval --topics 10 --pairs 10 --out ../eval/out
# 多种子重复（每次重新生成语料），输出均值 + bootstrap 95% 置信区间
uv run python -m app.cli eval --topics 10 --pairs 6 --repeats 3 --out ../eval/out

# 测试
uv run pytest -q
```

全部离线：LLM 客户端层用 `httpx2.MockTransport` 伪造 OpenAI 兼容响应，节点层用 `FakeLLM` 队列。跑测试不花钱。

### 界面

`GET /` 是 Vue 3 单页三栏：左边填画像与主题，中间按 SSE 逐个列出七个节点（耗时、花费、是否降级），右边出稿子、未达标项与守门人命中。

- **点开任一节点**：右侧抽屉三个页签——「产物」（这一轮的结构化结果）、「本轮 prompt」（只读，这个 run 当时用的文本）、「编辑下一版」（改完保存，下一次生成生效）。
- **不用先跑也能改**：中间栏底部常驻「角色 prompt」，七个角色各一行；点开是「当前生效版（只读）/ 编辑下一版」，保存后下一次生成生效。
- **模型也能在界面上换**：同一张「角色 · 模型 · prompt」表里每个角色一个下拉（网关的 19 个模型 + 价格表里的 4 个），即改即存。没登记价格的模型，成本显示成 `≥ ¥x（N 次未计价）`；读者与主笔同模型时，顶部与报告都标「非独立评审」。
- **prompt 可改，但每轮 run 自带快照**：`GET /prompts` 读当前生效版，`PUT/DELETE /prompts/{role}` 改写或恢复默认；run 启动时快照七段全文，`GET /runs/{id}/prompts` 查得到，HTML 报告里也有。改过 prompt 的 run 不能与 D9 的评测数字对比。
- **顶部能切回历史 run**（`GET /runs`）：旧 run 的 prompt 与产物仍是它当时那一份，不会被后来的编辑覆盖。
- 构建产物由后端托管（`frontend/dist`，`/assets` 静态挂载）：省掉一个容器，也不用配跨域（§10）。
- 没构建时 `/` 返回 503 并提示 `pnpm build`，不会静默给一个空页面。
- 技术栈：Vue 3 + TS + Vite + Pinia + Element Plus。`src/stores/run.ts` 是唯一的状态源，组件只读它；SSE 连接在收到 result 或组件卸载时关闭。
- 构建前可以先跑 `pnpm typecheck`（vue-tsc）——之前 `tsconfig.strict` 只是写着好看，现在真的会跑。
- 内联 diff 仍未做：目前靠顶部切换两版对照（§13 列的 ECharts 同理，当前页面用不上）。

## 局限

这类项目最容易在「局限」一节露怯，所以先说清楚：

- **没有真实互动数据。** 判定器的有效性只有内部验证（判别力 + 一致性），**不能**证明它等同于真实用户。
- **`bad` 档是构造出来的**（反向 prompt），它定义的是「我们能想到的 AI 味」，不是全部 AI 味。
- **标签级、选题级效果未验证**；赛道不固定，因此没有赛道专属规则与样本库。
- **轮次上限 3 是拍的**，没有做「为什么不是 2 或 5」的实验。
- 本轮**没有人工盲评**（E4），报告里已标明「无人工信号」。
- **读者与主笔同模型时不再具备独立性**：界面与报告会标「非独立评审」，这类 run 的数字不能与 `docs/samples/` 对照。
- **成本是下界**：选了没登记价格的模型时，显示 `≥ ¥x（N 次未计价）`——token 准确，钱只知道至少多少。
- 本项目本地运行，没有公网部署；面试官点不开 demo，用报告 + 录屏（待补）补偿。
