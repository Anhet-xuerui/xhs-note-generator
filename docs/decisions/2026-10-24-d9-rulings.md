# D9 评测 — 执行裁决（2026-10-24）

计划：`docs/superpowers/plans/2026-10-24-d9-evaluation.md`
规格：`docs/superpowers/specs/2026-10-23-xhs-multiagent-design.md` §12

## 裁决

- **统计手写，不引 scipy**：Kendall τ-b、Spearman ρ、Cohen κ、三档排序正确率各十行以内，可单测、无 80MB 依赖。代价：与 scipy 的数值实现存在极小差异，报告里不应与别人的 scipy 数字逐位比对。
- **`judge_draft` 返回 `Judgement(verdict, usage)` 而不是裸 `Verdict`**：E1/E2/E3 都要算「评分调用花了多少钱」，尤其 A 组要把评分成本单列（§12 口径统一）。
- **语料只用 `run_loop` 的交付稿，不走 D4 尾部**：评测看的是正文质量，封面/人味校订/守门人每个主题会多烧 3 次调用；省下来的钱用来扩大 N。代价：语料里的 good 稿没有经过 AI 味清理，与线上交付稿略有差异。
- **E3 的 C 组由调用方注入「同厂商读者」的 deps**：`Settings.load()` 会拒绝 `reader == writer` 的配置（这是 D4 的 C2 修复），所以 C 组用 `model_copy` 直接构造同厂商 provider，绕过启动校验。代价：C 组配置只能通过代码构造，不能写进 `.env`。
- **所有实验在同一个事件循环里跑**：`LLMClient` 缓存的 `AsyncOpenAI` 绑定 loop，多次 `asyncio.run` 会报 `Event loop is closed`（联调踩到）。`_evaluate` 因此是一个大的 async 函数。
- **流程偏差（诚实记录）**：`report.py` 与 CLI `eval` 子命令是先实现后补测试（前四个任务严格 RED→GREEN）。补测试时用 `--dry-run` 的端到端产物做了额外验证，但这两个模块没有「先看它红」。

## 全量跑法与预算

```bash
cd backend
uv run python -m app.cli eval --topics 10 --pairs 10 --out ../eval/out
```

- 估算：约 10 次语料 run + 10 次 bad 生成 + E1 30 次评分 + E2 60 次评分 + E3 三组各 10 篇（约 30 次 run）≈ 40–50 分钟、约 2–3 元人民币。
- 跑完先看 `eval/out/report.md` 的「判据是否达成」两行，再决定是否需要调判定卡（改动判定卡等于重跑，§12 冻结约束）。

## 全量跑（10 主题 / E3 每组 10 篇）

结果：E1 排序正确率 29%（判据 80%，未达成）、τ 0.60、权重不敏感；
E2 click κ 0.83（达成）/ save κ 0.41（未达成）/ ρ 0.77；
E3 通过率 A 0% → B 38%（4.7× token、4.5× 成本）→ C 43%（与 B 无显著差异）。
10 个主题里 7 个产出了成稿。样本：`docs/samples/eval-report-full.{md,html}`。

- 发现并修复的判据 bug：E2 原来只检查 click 的 κ，会把它报成「达成」。§12 要求 click 与 save 两个字段都 ≥ 0.6。已修（含回归用例），并用同一批数字重新渲染了报告——只有判据行变化，数值未动。
- 结论按「敢给负面结论」处理：判别力不达标照写，并给出 §16 的预案（改两两比较）；换厂商读者在本轮没有带来通过率优势，也照写。

## E1 改两两比较（第二次全量跑）

- 新增 `pairwise.py`：同一对稿子问两次、互换 A/B 顺序；两次指向同一篇才算一致，否则记 tie 并单独统计不一致率（12%）。
- 结果：绝对打分 29% → 50%，**两两比较 95%**（24 次比较）。§16 预案得到验证：测量方式比指标本身更决定判别力。
- E2 从「click κ 0.83 / save κ 0.41」变成「0.47 / 0.19」；E3 从「B 38% / C 43%」变成「B 12% / C 62%」。
  → 结论：**10 主题、单次运行的组间差异不可用**。唯一跨运行稳定的信号是 A 组（裸模型）两次都 0%，以及 B 组成本稳定在 11 万 tokens / 0.44–0.47 元。
