# 设计决策与取舍（一页纸）

> 面试投屏用。每条都是「选了什么 / 为什么不选另一条 / 代价是什么」。

## 1. 七个角色，每个都要过两道检验

**决策**：角色数封顶 7。新增角色必须同时满足「信息食谱与现有角色都不同」且「判断标准会与至少一个现有角色冲突」。

**为什么**：角色数量不是卖点，信息密度才是。原设计的第 8 个角色「侦察」（看爆款样本、归纳钩子）被删掉，
因为不采集平台数据时它的信息食谱退化成「模型的品味」，与策划重复——留着只是噪音。

**代价**：少了一个听起来更唬人的角色数。

## 2. 信息隔离写在代码里，不写在 prompt 里

**决策**：`context_builder(role, state)` 只按白名单取字段；三条隔离（读者看不到 `real_material`、策划看不到成稿、
主笔看不到规则库全文）各有单测 + 一条静态检查规则。

**为什么**：三个角色看到同一段 context，就退化成「同一个模型自我对话七次」——这是本项目的第一号反目标。

**代价**：新增字段要同时在白名单里登记，比「把 state 整个塞进去」麻烦。

## 3. 读者换一家厂商，是机制不是偏好

**决策**：写作用 DeepSeek，读者用另一家（当前是 GLM）。`READER_*` 缺失时启动即报错；与主笔同 base_url 同模型会被拒绝。

**为什么**：评价者与被评价者同模型、同上下文，是「模型给自己的稿子打高分」的根因。只换 temperature 不解决问题。

**代价**：多一组 key、多一个故障点；E2 的一致性检查才有意义。

## 4. 判定卡必须是可数字段，通过条件硬编码

**决策**：`Verdict` 七个字段（click / save / read_through / drop_at_sentence / comment_intent / objections…），
通过条件 `click & save & read_through ≥ 0.6 & 无硬伤` 由代码算，模型无权说「可以了」。schema 在评测前冻结。

**为什么**：不可数的评价（「整体不错」）既不能收敛也不能验证；让模型自己判通过，等于既当运动员又当裁判。

**代价**：改 schema 等于让全部评测作废——所以它被 `xhs-invariants` 的 C1/C2 锁住。

## 5. 规则先筛，模型后改（AI 味与合规同构）

**决策**：AI 味检测六类特征、违禁词三类 + 结构性两条，全部程序化；模型只按命中项改写、只判误报。

**为什么**：合规是二值判断，不能靠模型记忆；「最 / 第一」的误报（最后、第一次）纯正则处理不了，纯模型又不可靠。

**代价**：规则库要人工维护；误判率取决于规则质量，而这正是报告里「局限」的一部分。

## 6. 失败能降级就降级，不能降级就失败

**决策**：读者失败沿用上一轮判定；策划失败沿用已有角度；人味校订失败输出原文；
**主笔失败整个 run 失败**，**守门人失败直接 `gate_blocked`**。

**为什么**：没有稿子就没有意义；合规不能因为模型挂了就放行。降级必须留痕，成本必须逐调用累计。

**代价**：多写了不少分支；但「跑到一半炸掉」和「成本少算了」这两类事故都消失了。

## 明确没做的事

| 不做 | 理由 |
|---|---|
| 爬虫、采集平台真实数据 | 合规风险；拿不到真实互动数据也就无法校准外部效度，这一点写进局限 |
| 自动发布、接账号 API | 与「作品集」目标无关，风险远大于收益 |
| RAG | 没有检索需求，硬塞像到处找钉子 |
| Java / Spring | 单人作品里放两套后端语言，面试官第一反应是「为什么」而不是「厉害」 |
| 公网部署 | 本地运行 + 报告 + 录屏补偿；换来的是不用处理域名、备案、限流、日预算 |
